network-skill-lab · spec

Phase 2 內容系統

類型 正式開發（三層模型） 版本 v1 日期 2026-09-23，同日批准 撰寫 Fable 5.1（planner） 狀態 已批准

Phase 1 證明引擎能跑完一題。Phase 2 把引擎變成「不改程式碼就能長內容」的系統：文件、學習路徑、三種模式、隨機化參數、自檢、lint，以及五個各自驗證一個擴充點的 fixture lab。這個 phase 的產品是 DESIGN.md §3.9 那張擴充點表，lab 只是證據。

01目標與完成定義

  1. 不改程式碼新增內容。驗收時 planner 現場寫一個最小的新 lab（只有 lab.yaml、topology.yaml、setup、一個 check）放進 content/，重啟 nsl serve 後它出現在列表並可跑完。
  2. 三種模式都實測。五個 fixture lab 各自宣告的 modes 都能從瀏覽器跑完：tutorial 逐步自動前進；guided 即時打勾；real 只有工單、按「提交」才揭露、未全過可繼續。
  3. 隨機化成立。同一個 lab 連開三次，params 與 case 不同，precheck 皆通過；故意讓 precheck 失敗時最多重生 3 次後進 error 並顯示原因。
  4. lint 守門。nsl content lint 對一份故意弄壞的內容目錄一次列出所有錯誤，exit 非 0；CI 對 content/ 跑 lint。
  5. 文件與路徑可用。docs 頁與練習頁的文件面板顯示雙語 markdown；tracks 頁列出步驟與進度，完成的 lab 自動打勾，文件可標記已讀。
  6. k3s 可用。兩個 k3s lab 在瀏覽器跑完，provisioning 進度顯示到 Node Ready，冷啟動 < 30 秒。
  7. Phase 1 的驗收條目全部維持通過（回歸）；issue #24 的 flaky 測試修掉。

03待批的提案

以下十項於 2026-09-23 隨 spec 一併採納。

P1 precheck 失敗的重生 = 銷毀沙箱、重新選 case 與 params、重新 provision，最多 3 次
理由：D10 原文。Ubuntu 雙節點 provision 只要 2.7 秒，重來比「原地重跑 setup」簡單且乾淨；k3s lab 若 precheck 失敗代價較高，但 k3s 題的 params 通常不影響拓樸，作者應讓 precheck 幾乎不會失敗。
P2 進度存資料庫：progress(user_id, kind, ref, completed_at) lab 的完成由 passed 的 attempt 自動寫入；doc 由使用者按「標記已讀」寫入。track 頁的進度純粹由這張表推算。
理由：Phase 3 有多帳號，進度必須跟 user 走，不能放 localStorage。
P3 real 模式的提交語意 按「提交」→ 立刻跑一輪完整 checker → 全過則 passed；未全過則揭露本次結果（哪些過、哪些沒過，不含隱藏 checkpoint 的描述），狀態回 running，計時不停，可再提交，次數不限，submit_count 記錄。背景偵測在 real 模式照常跑但不廣播，用來記錄 first_passed_at。
理由：§3.3 的解讀，加上「不限次數」避免練習者被卡死。面試模式的限制留 Phase 5。
P4 k3s 節點預設關閉 traefik 與 metrics-server topology 的 node 可寫 k3s: { disable: [...] } 覆寫；預設 [traefik, metrics-server]。ingress 主題的 lab 自己把 traefik 打開。
理由：Phase 0 量到 helm-install traefik 讓系統 Pod 就緒多等 20 秒，且吃記憶體；大多數 k3s 題不需要它。
P5 五個 fixture lab 各驗一個擴充點
lab主題 / 等級驗證的擴充點modes
net-ip-01-link-down（既有，升級）net/ip · L1–L3params 產生器（cidr、ip_in）、cases（加 wrong-mtu）、precheck、tutorial 步驟、related_docstutorial, guided, real
net-route-01-wrong-gatewaynet/ip · L3三節點（web、gw、db）、gw 節點 ip_forward、visible: false 的隱藏 checkpoint、requiresguided, real
net-dns-01-resolvednet/dns · L2resolved / netplan DNS 設定壞掉、internet: false、choice 與 int 產生器guided, real
k3s-pod-01-crashloopk3s/pods · L2單節點 k3s-server role、Pod 的 kubectl 類 checkpoint、k3s 進度顯示tutorial, guided

理由：架構優先於內容。每個 lab 存在的理由是覆蓋 §3.9 的一列，不是湊數。
P6 lint 是純內容檢查，不碰 Docker，CI 一定跑 規則清單見 §07。腳本只檢查存在、可執行、bash -n 語法；不執行。
理由：GitHub runner 沒有 privileged 容器；執行類的驗證由 fixture lab 的整合測試負責。
P7 內容由 Opus 寫、Haiku 審，跟程式碼同一流程；每個 lab 一個 PR
理由：setup 與 check 腳本是會跑在 root 的 bash，品質要求跟程式碼一樣。文件的中文由 Opus 產出後 planner 抽查。
P8 隱藏 checkpoint 只在結果頁出現，任何模式的練習頁都不顯示；tutorial 模式不允許有隱藏 checkpoint（lint 擋）
理由：D9 原文；tutorial 的每步對應一個 checkpoint，隱藏會讓步驟斷掉。
P9 lab 列表改為主題樹分組，lab 詳情頁單獨一頁（說明、節點、相關文件、選模式開始）
理由：五個 lab 加上團隊之後的內容，平鋪列表會失控；模式選擇需要一個落點。
P10 params 產生器的隨機源：每個 attempt 一個 64 位元 seed，存進 attempts.params_json 旁的 seed 欄位
理由：可重現。之後面試模式或除錯時能用同一個 seed 重建同一題。

05內容格式：Phase 2 全規格

以 DESIGN.md §3.5 到 §3.8 為準，這裡只寫 Phase 1 子集之外要新增或明確化的部分。

params 產生器

gen欄位語意
constvalue固定值（既有）
cidrbase、prefix在 base 範圍內隨機取一個 /prefix 子網，例如 base 10.0.0.0/8、prefix 24 → 10.173.42.0/24；不與 mgmt 網段（172.16.0.0/12 由 Docker 用）重疊
ip_insubnet、index 或 range: [lo, hi]subnet 內第 index 個位址，或 range 內隨機一個，排除網路與廣播位址；同一 subnet 內不同 param 不重複
choiceof: [...]等機率選一
intmin、max閉區間整數

求值依宣告順序，後者可用 {{}} 引用前者（既有規則）。所有隨機都來自 attempt 的 seed。

cases 與 precheck

cases:
  - { file: cases/default.yaml, weight: 3 }
  - { file: cases/wrong-mtu.yaml, weight: 1 }
# cases/wrong-mtu.yaml
params: { fault: { gen: const, value: mtu } }   # 覆寫或新增 params（同名覆寫）
setup_env: { NSL_FAULT_MTU: "1200" }            # 額外注入 setup 與 checks 的環境變數
precheck: { script: precheck.sh, retries: 3 }    # 在 setup 之後、running 之前於每個 node 執行；任一 node 非 0 = 失敗

沒有 cases 的 lab 視為只有一個隱含的 default case。case_id 寫入 attempts。

checkpoints 與 tutorial

checkpoints:
  - id: gw-forwarding
    title: { zh: "...", en: "..." }
    node: gw
    script: checks/02-forwarding.sh
    visible: false          # 只在結果頁出現（P8）
    requires: [link-up]     # 只影響顯示順序與 tutorial 步驟順序
tutorial:                   # mode 含 tutorial 時必填；每個 visible checkpoint 恰好一步，順序須符合 requires
  - checkpoint: link-up
    instruction: { zh: "markdown", en: "markdown" }

其他新欄位

  • related_docs: [net/ip/guide, net/ip/playbook-no-connectivity]：練習頁文件面板的分頁，必須存在。
  • internet: false：mgmt 網路改為 --internal，節點無法對外；DNS 上游仍是 Docker embedded DNS，但外部名稱會失敗（Phase 0 觀察到的行為）。
  • topology node：k3s: { disable: [traefik, metrics-server] }（P4），只對 k3s-server 有效。

docs、topics、tracks

content/docs/net/ip/guide.zh.md            # id = net/ip/guide；同 id 必須 zh、en 都有
content/docs/net/ip/guide.en.md
content/topics.yaml                        # 樹狀，DESIGN.md §3.8；每個 lab.topic 與 doc 的目錄必須在樹中
content/tracks/network-basics.yaml         # DESIGN.md §3.7；step 的 doc / lab 必須存在，lab 的 mode 必須在其 modes 內

docs 的 markdown 第一個 # 標題作為文件標題；front matter 不用。

06模式語意

面向tutorialguidedreal
練習頁顯示步驟清單：目前步驟的 instruction markdown + 該 checkpoint；已完成步驟打勾工單 + 全部 visible checkpoint 即時狀態只有工單 + 「提交」按鈕 + 提交次數
checker 廣播是是否（只寫 DB）
結束條件同一輪全部 visible checkpoint 通過（隱藏不允許）同一輪全部 checkpoint 通過（含隱藏）提交時那一輪全部通過（含隱藏）
提交無無POST /api/attempts/{id}/submit：立即跑一輪，回傳 visible checkpoint 的結果與 hidden_failed 數量；全過 → passed
結果頁相同：全部 checkpoint（含隱藏）的最終狀態與 first_passed_at、提交次數、解答

tutorial 的「目前步驟」= 第一個未通過的步驟；使用者做完前一步，checker 打勾後 UI 自動捲到下一步。步驟不可跳過，但 checker 不管順序，做完後面的步驟一樣會打勾。

07lint 規則

nsl content lint [dir]（預設 NSL_CONTENT_DIR）。輸出每行 <path>: <rule>: <message>，全部列完才 exit 1；--json 給 CI 用。規則集 = Phase 1 的 §05 全部 + 以下：

  • params：產生器名稱與欄位合法；cidr 的 prefix 大於 base 的 prefix；ip_in 的 subnet 是已定義 param 或字面 CIDR；引用只能往前。
  • cases：檔案存在、weight 正整數、覆寫的 params 型別合法；至少一個 case 或零個。
  • precheck：檔案存在、可執行、bash -n 通過；retries 1 到 5。
  • checkpoints：requires 指向存在的 id 且無環；tutorial 模式下沒有 visible: false；tutorial 步驟與 visible checkpoint 一一對應且順序符合 requires。
  • related_docs 存在且 zh、en 皆在；topic 在 topics 樹中；tracks 的每一步存在且 mode 合法。
  • 所有腳本 bash -n 通過；checks 內不得出現 ip link set、systemctl、rm 、> 重導（啟發式，警告等級）。
  • topology：k3s 選項只出現在 k3s-server；internet 為布林。

08k3s 支援

  • provider 對 k3s-server 依 disable 寫進 /etc/rancher/k3s/config.yaml（bootstrap 已讀 NSL_K3S_DISABLE 環境變數，image 端小改）。
  • provisioning 進度加一步 k3s：provider 在 bootstrap 後輪詢 kubectl get nodes 直到所有 k3s 節點 Ready（上限 90 秒），再跑 setup。這一步只有 k3s lab 才會出現。
  • k3s lab 的 setup 可以用 kubectl（KUBECONFIG 已由 bootstrap 寫進 profile；setup 以 root 執行時需 export KUBECONFIG=/etc/rancher/k3s/k3s.yaml，引擎統一注入這個環境變數給 k3s-server 節點）。
  • 整合測試新增 k3s 單節點 lab 的完整流程（build tag integration，本機跑）。

13風險

  • k3s lab 的 provisioning 時間：Phase 0 量到 16 到 21 秒到 Ready；關 traefik 後預期更短，但 WSL 記憶體吃緊時會變慢。T4 先量再定 UI 的等待上限。
  • 隨機參數與 checks 的耦合：作者容易在 check 腳本寫死位址。lint 加啟發式警告（腳本內出現 10.0. 這類字面 IP），不擋。
  • real 模式的背景偵測與提交同時跑：兩者共用 checker 的 sweep，需要互斥；T3 的單元測試要涵蓋。
  • 內容量：四篇雙語文件與五個 lab 是本 phase 最花時間的部分，但不影響引擎驗收；若時間不夠，先砍 net-dns-01 與 k3s-svc-01，擴充點覆蓋改由測試 fixture 補。
