Phase 4 遠端 Runner 與 VM

類型 spike + 正式開發 版本 v1 草案 日期 2026-09-25 撰寫 Fable 5.1（planner） 狀態 待批准

到 Phase 3 為止，控制面與沙箱在同一台機器，這是 R6 記錄的上線前置條件。Phase 4 把 Runner 介面真正變成遠端的：成員在自己的主機跑 nsl runner，用 token 連回控制面，題目在他們的機器上執行；控制面主機不再需要 Docker。同一個 phase 先用 spike 驗證 VM provider（libvirt + KVM + cloud-init），通過才正式化，讓 environment: vm 的擬真題有落點。

01目標與完成定義

  1. 遠端執行。一個 nsl runner 在另一台主機（或同機另一個使用者 / 容器內的 Docker）以 token 連上控制面，使用者從瀏覽器開題，沙箱建在 runner 主機，terminal、checkpoint、錄影、指令歷史全部如常；控制面主機上沒有任何 nsl.managed 資源。
  2. 斷線有交代。runner 斷線時進行中的 attempt 在 10 秒內進 error（原因「runner disconnected」）並顯示於 UI；runner 重連後其殘留沙箱被清掉，可立刻再接新題。
  3. 多 runner 並存。控制面內建的 in-process runner（若主機有 Docker）與遠端 runner 同時各跑一題；每個 runner 的容量分別計算，admin 頁看得到每個 runner 的名稱、能力、使用量與連線狀態。
  4. VM spike 有結論。§08 的五項驗證有實測結果寫回 docs/PHASE4-RESULTS.md，並據此決定 T4 做或延後。
  5. VM lab 可跑（條件式，spike 通過才算入）：一個 environment: vm 的 lab 在 VM runner 上從瀏覽器跑到 passed，冷啟動 < 90 秒。
  6. 保留策略。nsl prune --older-than 30d 刪除舊 attempt 的錄影與紀錄；admin 頁顯示磁碟用量；#71 修好。
  7. 回歸。Phase 1 到 3 的驗收條目、make test-integration、make test-content 在 in-process runner 上維持通過；同一套 content 測試也能指向遠端 runner 跑一次。

03待批的提案

批准這份 spec 即視為採納，有異議請指出編號。

P1 runner 外連控制面，單一 WebSocket，JSON 控制訊息 + 帶 stream id 的二進位串流 控制面不主動連 runner，runner 主機不需要開 port、不需要公網。同一條連線承載 RPC（Provision、Exec、Destroy、GC、Health）與 PTY 串流（每個 terminal 分頁一個 stream id）。
理由：成員的機器多在 NAT 後面；一條連線最簡單，斷線語意也單一。
P2 認證用每個 runner 一個靜態 token，admin 在管理頁建立，DB 只存 argon2id 雜湊 token 建立時顯示一次；runner 以 NSL_RUNNER_TOKEN 或 --token-file 帶入。
理由：與帳號同一套雜湊與流程；不需要 PKI。
P3 斷線語意：控制面在 10 秒內把該 runner 上所有進行中的 attempt 標為 error；runner 自己保留沙箱最多 2 分鐘等重連，重連後控制面下令銷毀 不做「重連後接續」：pty 已斷、checker 已停，接續的複雜度不值得。
理由：D13 預期單人使用，斷線是例外；清楚的失敗勝過半吊子的恢復。
P4 排程：依 lab 的 environment 過濾有能力的 runner，取「使用中沙箱數 / 容量」最低者；全部滿了回 429 in-process runner 的容量沿用 NSL_MAX_SANDBOXES；遠端 runner 由 nsl runner --max-sandboxes 宣告。控制面在 /api/admin/stats 與 429 回應中列出每個 runner。
理由：最簡單且可解釋的策略；lab 綁定特定 runner 的需求還沒出現。
P5 VM 的 Exec 走 qemu-guest-agent，terminal 走 mgmt 介面的 SSH guest-agent 不經過 VM 的網路堆疊，題目把介面全關 checker 仍能跑（R4 的 VM 對應）；SSH 用 runner 產生的一次性金鑰，走 mgmt 網路（題目不准動 mgmt，與容器規則相同）。
理由：guest-agent 的 exec 沒有互動 pty；SSH 是最穩的 pty 來源，mgmt 永遠通。
P6 VM image 由 images/vm/build.sh 從 Ubuntu 24.04 cloud image 產生 qcow2，預裝與 nsl/node 相同的 66 個套件與 bootstrap 腳本 每個 VM 用 backing file 開 overlay，冷啟動只複製差異層。
理由：與容器同一份工具清單與 bootstrap 契約，內容不用分兩套。
P7 VM spike 的門檻：runner 主機必須有 KVM；WSL2 沒有就在你的另一台機器或實體 Linux 上驗，驗不到就把 T4 延到 Phase 5
理由：沒有 KVM 的 QEMU 純軟體模擬慢到不能當練習環境；這是硬體前提，不是程式問題。
P8 保留策略只做手動與定時的 prune，不做配額 nsl prune --older-than 30d [--dry-run] 刪終態超過 N 天的 attempt（列 + 錄影檔）；NSL_PRUNE_AFTER 設定後 serve 每天執行一次。admin 頁顯示總用量與最舊紀錄日期。
理由：配額需要使用數據；prune 先把磁碟守住。
P9 nsl runner 與 nsl serve 是同一個 binary；runner 主機只需要 Docker（或 libvirt）與這個檔案
理由：D3 all-in-one 的延伸；版本一致由 handshake 檢查（協定版本不合直接拒絕並提示）。
P10 in-process runner 保留，控制面主機沒有 Docker 時自動停用，不報錯
理由：單機開發與 CI 仍用它；正式部署時控制面主機可以完全不裝 Docker。

04架構變更

internal/
  runner/         Runner 介面不變；+ Registry（多 runner）、Scheduler、RunnerInfo{Name, Capabilities, Capacity, Active, Connected}
  runnerproto/    協定：訊息型別、編碼、stream 多路復用（純函式，兩端共用）
  runnerclient/   runner 端：連線、重連、把 RPC 轉呼叫本地 provider、PTY 串流轉發、保留沙箱 2 分鐘
  runnerserver/   控制面端：接受 runner 連線、token 驗證、把 Runner 介面實作在連線上（RemoteRunner）
  provider/vm/    T4：libvirt + QEMU/KVM + cloud-init（條件式）
  attempt/        Start 改走 Scheduler；runner 斷線 → error；runner_id 落 DB
  api/            admin runners 端點；stats 加 runners；429 帶 runners
  store/          runners 表、prune 查詢
cmd/nsl/          + `runner`、`prune`、`runner token` 子指令（token 建立也可在 admin 頁）
images/vm/        build.sh、cloud-init 範本
spikes/phase4/    VM 驗證腳本與結果

依賴方向：attempt → runner 不變；runnerserver 實作 runner.Runner；runnerclient → provider/*。PTY 位元組經控制面轉發（錄影仍在控制面完成），不做 runner 直連瀏覽器。

05Runner 協定

連線：runner → wss://<控制面>/ws/runner，header Authorization: Bearer <token>
握手：runner 送 { "type": "hello", "proto": 1, "name", "version", "capabilities": ["container"], "capacity": 3 }
      控制面回 { "type": "welcome", "runner_id" } 或關閉（4001 版本不合、4003 token 無效）
心跳：runner 每 15 秒 { "type": "ping", "active": n }；控制面 30 秒沒收到視為斷線
RPC（控制面 → runner，text frame）：
  { "type": "call", "id", "method": "provision"|"exec"|"destroy"|"gc"|"health"|"open_terminal"|"resize"|"close_terminal", "params": {...} }
  runner 回 { "type": "result", "id", "ok": bool, "value": {...} | "error": "..." }
  provision 的 progress：runner 送 { "type": "progress", "id", "step" }
串流（binary frame）：前 4 bytes 為 stream id（open_terminal 的回傳值），其後為 pty 位元組；雙向同格式
  runner 送 { "type": "stream_closed", "stream": id }（shell 結束）
方法參數即 runner.SandboxSpec 等既有型別的 JSON；Exec 的 stdin 以 base64 放進 params（腳本內容都很小）；ExecResult 同樣回 base64 的 stdout/stderr。

控制面對每個 runner 連線建立一個 RemoteRunner，實作 runner.Runner：方法 = 送 call 等 result，逾時與 ctx 取消都會送 cancel（runner 端盡力中止）。

06控制面與 runner 端

控制面

  • runners 表（§11）與 admin 端點：建立 token（回明文一次）、列表（名稱、能力、容量、使用中、連線狀態、最後心跳、版本）、撤銷。
  • Scheduler（P4）；attempts.runner_id 記名稱；斷線處理（P3）；Recover 對每個已連線的 runner 送 gc（instance 標籤沿用 runner 名稱）。
  • in-process runner 以名稱 local 註冊，能力 container，容量 NSL_MAX_SANDBOXES；主機沒有 Docker 時不註冊（P10）。
  • 錄影、指令歷史、checker 完全不動：它們只認 runner.Runner。

runner 端

  • nsl runner --url wss://host --name lab-01 --max-sandboxes 3 [--provider docker|vm] [--instance ...]，token 從 NSL_RUNNER_TOKEN 或 --token-file。
  • 重連：指數退避 1 到 30 秒；重連成功後回報仍存在的沙箱清單，由控制面決定銷毀。
  • 本地 provider 沿用 provider/docker（instance 標籤 = runner 名稱），VM 用 provider/vm。
  • 日誌與健康：--metrics-listen 不做；健康以 hello / ping 為準。

08VM spike（T0，planner 直接做）

#驗證通過條件
V1runner 主機 KVM 可用（/dev/kvm、libvirtd、virsh capabilities）；WSL2 需 nestedVirtualization=true能以 KVM 加速啟動一台 VM；否則觸發 P7
V2用 build.sh 產生的 qcow2 + cloud-init（user-data 注入 SSH 金鑰與 bootstrap 環境變數）開機從 virsh create 到 qemu-guest-agent 可 ping < 45 秒；到 SSH 可登入 < 60 秒
V3guest-agent exec 跑 check 腳本，含把所有介面關掉、nft 全 DROP 後exec 仍成功，回傳 exit code 與輸出
V4兩台 VM 接 libvirt 隔離網路（每條 link 一個 <network> 無 DHCP 無 NAT）+ mgmt NAT 網路；bootstrap 用 netplan 設位址eth1 互 ping 通；mgmt 不受題目影響
V5資源：每台 VM 記憶體 512 MB 到 1 GB，兩台並存的主機負載與磁碟兩台 VM 冷啟動總計 < 90 秒，記憶體有數字

結果寫 docs/PHASE4-RESULTS.md §VM spike；V1 失敗即記錄並把 T4 延後，其餘 task 照常。

09VM provider（T4，條件式）

  • libvirt 經 libvirt.org/go/libvirt（需 cgo）或 virsh CLI 包裝；spike 決定，傾向 CLI 包裝以維持純 Go 建置。
  • Provision：建 mgmt + link 網路 → 每個 node 建 overlay qcow2 → cloud-init ISO（hostname、SSH 金鑰、NSL_* 環境寫進 /etc/nsl/bootstrap.env）→ define + start → 等 guest-agent → bootstrap（guest-agent exec）→ setup。
  • OpenTerminal：SSH 到 mgmt IP（golang.org/x/crypto/ssh，nsl 使用者、一次性金鑰）；Exec：guest-agent。
  • Destroy：destroy + undefine + 刪 overlay 與 ISO；GC 依 domain metadata 的 instance 標籤。
  • role：ubuntu / ubuntu-nm 先做；k3s 在 VM 內理論可行但不在 Phase 4 驗證。

10保留與清理

  • nsl prune --older-than <dur> [--dry-run]：刪除終態且 ended_at 早於門檻的 attempt（cascade）與其錄影目錄；印出筆數與釋放大小。
  • NSL_PRUNE_AFTER（如 720h）：serve 啟動後每 24 小時跑一次。
  • admin stats 加 oldest_attempt_at。
  • #71：Destroy 等容器真的消失再刪網路，重試視窗 15 秒；nsl gc 回報數量。

11資料模型

  • migration 0004：runners(id TEXT PK, name TEXT UNIQUE, token_hash TEXT, capabilities TEXT, capacity INTEGER, created_at, last_seen_at, revoked_at, version TEXT)。
  • attempts.runner_id 存 runner 名稱（既有欄位）。

13風險

  • PTY 經兩層 WebSocket 轉發的延遲：目標 < 50 ms 額外延遲；T2 量。
  • KVM 在 WSL2：需要 Windows 11 與 .wslconfig 設定；不確定你的環境是否允許，這就是 T0 的意義。
  • libvirt 的 Go 綁定需要 cgo：與 P4 的純 Go 原則衝突，傾向 virsh CLI 包裝。
  • runner 主機是 root 等級的攻擊面：token 外洩等於該主機的 Docker 控制權；README 要講清楚，且 token 撤銷要立即生效。
